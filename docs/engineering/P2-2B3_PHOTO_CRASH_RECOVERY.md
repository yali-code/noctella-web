**Narrow prevention change plus tested diagnosis/design; automatic reconciliation is BLOCKED.** No automatic scanner, quarantine move, deletion, schema migration, repair of canonical files, outbox recreation or scheduler is enabled. `PRODUCT_PHOTO_DISK_STAGING_ENABLED` remains disabled by default. ## Concrete runtime change

Before this change, `uploadPhotoWithStorage` in `aiIntakePhotos.ts` deleted the newly encoded private source after *any* locked-insert error. The disposable fault-injection probe commits the actual AI row and then throws instead of returning the transaction result. The old service catches that simulated lost acknowledgement and deletes a file still referenced by the committed row. This is a reproduced ambiguity bug, not a claim about historical production failures.

When disk staging is enabled, the new catch retains the source, closes shared image admission and throws the fixed 503 `PHOTO_STORAGE_UNAVAILABLE` / `AI photo persistence requires recovery`. It does not guess whether COMMIT succeeded. The same policy applies conservatively to definite rollback errors: availability/storage are traded for preserving possibly referenced bytes. New enabled image work fails closed; waiting work follows the existing admission shutdown/drain semantics. No lease is released before native storage work has settled.

The scope is persistence errors **after** storage returned, not validation/precheck/encoding errors before a new source exists. Normal storage error cleanup and successful upload contracts remain unchanged. Flag-OFF compensation remains unchanged; this PR does not claim to solve legacy lost-acknowledgement behavior. The feature requires restart for policy changes. After an enabled ambiguity error, an operator must inspect authoritative DB state before any restart/retry; random-key AI uploads have no request idempotency identity and must not be blindly retried.

## What the offline prototype does

`scripts/photo-crash-recovery/plan.cjs` is a pure retain-only reference model. It consumes a supplied snapshot, has no DB/FS mutation capability and is not imported into application/runtime routes or schedulers. It protects main/thumbnail filename/storage-key/local-URL references, AI private keys and deterministic finalization identities, and photo outbox aggregate/payload references, including completed events. Malformed/dangling outbox state is an explicit blocker. Missing or zero-byte referenced files are anomalies, not cleanup candidates. Unknown keys, symlinks/special entries, DB outage, incomplete reference coverage and unfenced writers never authorize mutation.

Every result sets `safeToMutate=false`, `automaticRetry=false` and action=retain. Repeated snapshots produce identical plans. This is useful diagnosis but **not a production recovery mechanism or a complete reference census**. Files are not age-deleted, moved, overwritten, repaired or marked Ready. Private source retention, canonical IDs/keys/order/primary/alt, image recipes, outbox transactions, backup manifests and marketplace behavior are preserved.

## Proposed durable recovery protocol — future gate, not implemented

1. Persist a server-generated operation UUID, owner boot epoch, fencing generation, intended input/output keys and workflow/entity identity **before creating any file**. Track receiving, encoding, prepared, committing, committed, abandoned and review-required states. Allocate canonical/storage IDs once and persist them so a retry cannot create a new identity. Record recipe/source hash, complete output hash/length and physical root/device aliases; complete native work before marking prepared. A filesystem manifest alone is not authority.
2. Commit photo/AI metadata, promotion outbox and the operation's committed state in the same domain transaction. On any acknowledgement failure, retain bytes and stop ingress; re-read the authoritative primary only after the original transaction settles. Do not infer rollback from timeout, missing response or a stale replica. A prepared operation without a complete commit decision is review-required.
3. Before maintenance, fence **all** HTTP/background/legacy writers, outbox promotion/deletion, finalization and existing cleanup. Use a DB-coordinated maintenance generation plus actual process/deployment ownership; expire a lease only after fencing the former owner. PostgreSQL advisory/row locking and SQLite writer serialization must have equivalent ownership semantics. PID existence, process-start watermark and TTL alone are insufficient.
4. Read a consistent primary DB snapshot and revalidate under that fence immediately before a mutation. Check photo rows/keys/URLs, all AI rows/status/result identities, outbox aggregate and key payloads/status/locks, publishing snapshots and existing retention/backup ownership. Treat unknown schema/status/coverage, DB outage, symlink/hardlink alias, changed inode/size/hash or incomplete scan as a blocker. Referenced canonical/private bytes never move automatically.
5. Conservative quarantine requires proven operation ownership + a terminal/fenced abandoned owner + no protecting references. Write a durable quarantine-intent journal first; preserve immutable bytes in a separate private root with exclusive no-overwrite destination and integrity metadata. A same-device hardlink can avoid duplicate payload space, but shared aliases must remain immutable and be audited. Never use an overwriting rename/copy as a shortcut. Removing an original name is a separate fenced transition after authoritative revalidation; retain at least one verified copy. Canonical ambiguities require operator review. No quarantine garbage collection belongs in this phase.
6. Restart reconciliation uses operation ID + fencing generation + source/destination hashes to resolve journal-intent-only, two-name and completed-name states idempotently. If any journal/DB/file combination is not proven, retain both and stop. A referenced missing/zero file is an integrity incident; never synthesize a success row or outbox event. Complete deterministic AI preparation may resume through the existing verified service; corrupt conflicting output requires operator review and a separately journaled repair/restore.
7. TTL is a review scheduling bound, never deletion authority. Choose lease/heartbeat timeouts from measured maximum upload/transform/drain times and clock/deployment assumptions, not a guessed age. Historical unjournaled files can be inventoried/reviewed but cannot be automatically proven abandoned; do not backfill fabricated ownership. Protocol adoption requires an explicit migration/rollout design coordinating older writers and Sprint96 cleanup.

## Disk-space/ENOSPC and rollback

Existing ingress uses42MiB software reservation/request, three admissions and a128MiB staging inventory budget; output checks happen after native encode. These are not a hard filesystem quota. Private AI output, canonical files, derivatives, accumulated crash files and DB/WAL space must be included in a future global volume inventory. Separate filesystem quota/free-space policy is a gate, not part of this PR.

Reserve DB/WAL/journal/evidence headroom before accepting new work. ENOSPC/EIO/permission failure must close ingress and retain state; no fallback deletes canonical, AI source, quarantine or S3 backup bytes. Creating a quarantine link can itself fail for inode/metadata space; retain the original and journal intent. Cross-device quarantine/copy requires space for a full verified copy and cannot silently delete the source to free room. Bounded reporting must not compete with recovery metadata or fill the disk.

Rollback for this narrow change: keep both features disabled; no schema migration exists. Reverting the enabled AI safeguard restores the old possible destructive compensation, so do not re-enable that path on rollback. Preserve retained disks and authoritative DB/outbox history, inventory/review and reconcile before restart. Never delete staged/canonical files merely to reopen admission. Any future durable journal must remain readable after rollback; do not downgrade to an unaware writer with unresolved operations.

## Test methodology and limitations

The fault injector calls actual storage/services/locked transactions on migrated real schemas. Tiny synthetic32×24 PNGs/WebPs avoid customer data and unrelated OOM benchmarking. Input directories are constructed by the fixture at the storage boundary, not parsed through an HTTP multipart listener. Real existing 24-MP HTTP/OOM evidence in #394/#397 establishes retained ingress/zero-output motivation; this task does not rerun or claim the384-MiB gate.

Linux CI kills the API child with SIGKILL at deterministic handshakes and waits for physical process close, retains disks, then starts two new inventory processes/connections. PostgreSQL remains running, matching an API-process death; only unique disposable migrated schemas in the local CI PostgreSQL16 service are used. SQLite uses WAL like the file-backed API runtime and its own engine performs restart recovery. Local Windows termination is labelled as Windows, not POSIX kill evidence. The zero deterministic finalization output is an explicit interrupted-open fault injection, not a claim to have sampled libvips halfway through a native write.

Boundary cases: AI reserved output, encoded-before-row, uncommitted row, committed-before-response, lost-acknowledgement and definite rollback; first product hardlink, product pre/postcommit and lost acknowledgement; finalization pre/postcommit, first deterministic output and injected zero output; Instagram temp-before-link. Assertions cover DB/outbox atomicity, immutable file hashes and physical hardlink identity, deterministic IDs, source retention, repeated successful/failed finalization retries, no duplicate outbox, gated admission close and legacy wrapper bypass. Planner tests cover reference anomalies, missing files, outbox protection, invalid references/entries, DB outage and live writers.

This is not a crash soak, power-loss/fsync guarantee, concurrent multi-process fencing implementation, full quota validation, production readiness or live-data recovery. Full automatic recovery remains BLOCKED pending the durable protocol and approval gates above. Flag-OFF acknowledgement ambiguity remains an explicitly unresolved legacy risk; existing compensation regressions are preserved.

Raw Linux results, artifact hashes, source revision and successful source CI566 are recorded in `photo-crash-recovery-evidence/REPORT.md` and the Draft PR. No secrets/DB URL/provider credentials/customer media are logged or stored in probe evidence.

## PostgreSQL compatibility blocker discovered during validation

The initial Linux run38543210243 passed all15 SQLite crash cases but all15 attempted PostgreSQL service cases failed before their handshakes. The baseline intake repository writes ISO timestamp strings to Date-mode PostgreSQL columns. Instrumented confirmation records the exact TypeError/stage in subsequent artifacts. No production schema is adapted and no test-only timestamp mapper is inserted to disguise compatibility. Only this specific preflight failure is reported as BLOCKED/skipped; unrelated failures still fail CI.

PostgreSQL protocol validation is explicitly separate: migrated real tables, actual local image storage, native SQL transactions, SIGKILL before/after COMMIT, and a committed outbox-only fixture whose keys must remain protected without a photo row. A fourth case seeds an intake directly with server-default timestamps and exercises the actual AI storage/service error handler: it must retain the private source and close admission when persistence fails. These cases do not constitute successful end-to-end PostgreSQL photo upload/finalization acceptance. The ISO-to-Date repository compatibility and complete PostgreSQL photo-service matrix remain unresolved gates, rather than expanding this recovery PR into a broad driver migration.
