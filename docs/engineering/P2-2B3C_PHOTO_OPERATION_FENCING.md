## Why a journal-only runtime patch is unsafe

The current asynchronous storage APIs do not accept operation/generation capabilities. A prior DB read cannot authorize a later mutation after ownership changes. The experiments demonstrate this on real existing LocalStagedProductPhotoStorage.deleteProductPhoto: after reclaiming the proposed journal generation, the old caller still deletes two explicitly created synthetic files inside the newer generation directory. This is a deliberate counterexample on disposable files, not a claim that such a journal exists today or that a production incident followed this schedule.

A second counterexample exercises the actual SQLite intake lock capability. Returning a Promise triggers SQLITE_ASYNC_AI_INTAKE_LOCK_TRANSACTION_CALLBACK_REJECTED and rolls back DB work, but a paused asynchronous callback resumes and overwrites a synthetic newer-owner file afterward. Rejecting a Promise does not cancel the callback/native encoder or revoke its open descriptors. Therefore wrapping current await-based storage work in existing SQLite transactions is not a safe portable implementation.

A third, positive experiment keeps an independently connected reclaimer outside a database-held, synchronous publication critical section: SQLite BEGIN IMMEDIATE and PostgreSQL SELECT FOR UPDATE yield SQLITE_BUSY and 55P03 respectively under bounded lock timeouts. Reclaim succeeds after release. This proves that particular cooperative schedule, not distributed DB/filesystem atomicity, cancellation of in-flight native work or safety after connection loss.

The smallest *safe deliverable here* is a test-only claim/transition model and explicit integration design. Shipping an unused production journal would not establish ownership; enabling it on only HTTP uploads would leave finalization, outbox handlers, legacy paths and existing cleanup unfenced. No speculative runtime layer is shipped.

## Proposed authoritative records — additive migration proposal, not deployed

1. photo_operations: stable server UUID; workflow kind; entity/intake/product identity; immutable allocated photo/storage/derivative keys; recipe version; expected source identity/hash once established; current owner boot UUID and claim nonce; monotonic generation; lifecycle; lease deadline; created/updated timestamps; authoritative photo/AI/outbox references; protocol version and rollout epoch. No customer filenames, bytes, credentials, signed URLs or arbitrary paths in the journal.
2. photo_operation_generations: composite (operation_id,generation), unique (operation_id,claim_nonce), owner boot UUID, state/lease/audit timestamps, superseded reason. Never reset/reuse a generation or forget old generations during reclaim. A retried claim nonce resolves to its existing historical generation, never a fresh ownership grant. Production generations use validated BIGINT/string handling and explicit overflow refusal.
3. photo_operation_artifacts: one row per input/main/thumbnail/private/Instagram derivative, logical root alias and relative key; generation or immutable canonical role; planned/materialized/sealed state, byte length, SHA-256, source/recipe identity and optional device/inode observations. Filesystem metadata alone is not authority. Unique generation paths and immutable canonical allocation prevent name reuse.
4. Durable reference links: operation/artifact to exact photo, AI record, outbox aggregate/payload/idempotency key and later publishing reference domains. Retain links/history after domain row disappearance. Unknown historical records cannot be assigned fabricated ownership.

A production migration would be additive and independently reviewed for both DBs. No backfill invents generation ownership for existing files. Nullable references accommodate pre-file intents but never authorize mutation. Journal history is retained on rollback. Application rollback may disable adoption and retain files; it must not downgrade unresolved operations to an unaware writer. The fixture DDL is explicitly probe_photo_* and is applied only inside disposable test databases, not src/db migrations.

## Atomic contracts

- Begin: durable intent and initial generation in one transaction before file creation. Duplicate stable operation ID cannot alter owner/keys; compare immutable identity and return the authoritative existing result or conflict. Owner is a boot identity, never a PID.
- Claim/reclaim: expected-generation conditional update and insertion of the new history row in one transaction. A live lease cannot be stolen. At exact expiry, reclaim may advance a generation for *cooperating generation-isolated writers*, never grant deletion or takeover of shared mutable paths. Reusing an old nonce rolls back rather than creating ABA ownership.
- Heartbeat: matching operation/generation/boot/nonce and still-live lease required; expired generations cannot resurrect. Lifecycle and audit fields change atomically in both operation and generation rows.
- Prepare: only after native work and all descriptors settle; verify nonzero length, digest, source/recipe and bounded dimensions. Persist artifact sealing under the token. Zero bytes, unknown ownership, abort, disk-full and DB outage retain state for review, not prepared success.
- Commit: revalidate current owner/generation/live lease and immutable identity under the same domain transaction that creates photo/AI metadata, promotion outbox and committed operation/reference links. Terminal committed is not reclaimable. Lost acknowledgement resolves by rereading authoritative primary operation + exact photo/outbox links; a failed response is not rollback evidence. Retry must not duplicate identity/event or prepare new bytes for an already committed operation.
- Aborting/shutdown: stop new claims; signal work; await actual native/stream settlement. No early release/reassignment of shared resources based on cancellation alone. After process death, retain all generations; only a later cooperative claim uses new private paths. Review-required blocks automatic reclaim in the fixture.

SQLite: obtain the writer reservation before reading authority (BEGIN IMMEDIATE); callbacks participating in the commit must remain synchronous. PostgreSQL: lock the operation row FOR UPDATE and acquire domain locks in a single documented order (rollout epoch, operation, intake, product, artifact/reference records). Use expected generation in writes, not a read followed by a later unguarded write. Default isolation plus row locks is sufficient for the tested single-operation CAS, not a full reference census.

Production expiry should use authoritative DB clock within the claim transaction, not request/worker clocks. A provisional TTL/heartbeat must be justified by measured drain/encode/DB-lock durations; this task does **not** choose a production timeout from tiny fixtures. Prototype clocks are deterministic injected integer milliseconds, not a demonstrated production lease policy. Clock jumps affect availability and must never become deletion authority.

## Filesystem fencing and integration sequence

1. Introduce a coordinated rollout epoch and quiescence gate covering *every* HTTP, background, legacy, cleanup and publishing writer. Older deployments and flag-OFF processes cannot silently participate. Keep current OFF behavior until this compatibility gate has an explicit rollout plan.
2. Allocate operation/keys and register all artifacts durably before ingress. Long asynchronous receives/Sharp work write only operations/<id>/g<generation>/... paths. A stale encoder with an already-open descriptor can finish only its old generation file; it cannot reach a newer namespace through the storage capability. No directory reuse, symlinks or caller-selected paths.
3. Seal outputs after native work settles. Future API must expose narrow sealed publication operations, not the prototype's arbitrary callback. Immediately before publication, validate owner/fence, reference set, generation and source/recipe under DB serialization. Use a short synchronous no-overwrite hardlink publication on the same filesystem for SQLite; PG must use equivalent immutable semantics. Cross-device EXDEV fails closed; no overwriting copy fallback or automatic removal. Keep canonical IDs, URLs, ordering, primary/alt and original recipe unchanged.
4. Commit domain/outbox/operation atomically. Filesystem and DB cannot share a transaction: crash after publication but before COMMIT leaves retained intent-owned aliases; DB rollback never triggers blind unlink. No canonical zero-byte reservation in the new protocol. Already-present conflicting/hash-unknown output requires review.
5. Add explicit native-work drain and DB connection-loss fault injection. A DB row lock alone is **not** a kernel filesystem fence: connection loss can release it while the callback still runs. Generation namespaces plus immutable no-overwrite publication must remain safe even then; CAS must reject stale metadata finalization. Any stronger no-stale-publication guarantee needs a separately designed storage broker/OS capability with verified revocation. Do not claim it from a preflight or this model.
6. Only after every writer honors capabilities and durable identity, run full real workflow races/lease expiry/connection loss/SIGKILL and unchanged resource acceptance. Reconciliation, full reference coverage and any future operator-authorized repair belong to P2-2B3D/#396. No automatic deletion/quarantine is proposed by this phase.

## What the executable prototype proves and does not prove

scripts/photo-operation-fencing contains fixture SQL, a guarded DB adapter and deterministic tests. It is not imported by application code. It validates create/conditional claim/renew, nonce uniqueness/ABA refusal, retained generation history and photo+outbox+operation rollback/commit on real DB engines. Commit checks exact authoritative photo/event links, but it does not implement AI/Instagram-specific production identities or all artifact/reference schemas. The trusted test callback is intentionally not a production interface.

Positive tests cover independent worker processes competing for a claim, exact expiry, preflight race with stale callback refusal, a held old-generation FD that cannot alter a newer namespace, rollback and lost acknowledgement, zero-byte retention/review, abort, outage-before-callback, row/writer lock serialization and six SIGKILL restart phases per engine. Existing retain-only planner protects a real historical outbox-only reference irrespective of DeadLetter status. Negative tests intentionally reproduce unsafe existing compensation and async SQLite guard behavior; a passing counterexample is evidence of a blocker, not a safety claim.

Remaining unproven: all real workflows using durable intents; full root/reference census; safe mutation after DB connection loss; startup/mixed-version maintenance epoch; authoritative production clock and timeout policy; schema rollout; native descriptor sealing; cross-device/disk-full/fsync/power loss; full API memory acceptance. Prototype IDs/clocks/one-output paths are bounded synthetic fixtures, not production data contracts.

## Privacy, failures, rollback and evidence

Only synthetic bytes/tiny parent image fixtures, localhost disposable PostgreSQL schemas and guarded os.tmpdir/noctella-photo-fence-* roots are used. Workers log no DB URL or credentials. No provider/network call is made by experiments; DB traffic is localhost only.
