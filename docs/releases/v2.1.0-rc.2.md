# Noctella ERP/Web v2.1.0-rc.2

- Release type: Release Candidate
- Package version: `2.1.0-rc.2`
- Planned Git tag: `v2.1.0-rc.2`
- Base branch: `main`
- Documentation baseline: completed work through Sprint 122 on `main`
- Tag target: not yet selected. The tag has not been created and requires completed review and
  isolated staging acceptance for this candidate.
- Release status: isolated staging acceptance pending until completed

`v2.1.0-rc.1` remains published, unchanged, and continues to point at its original commit
(`01ddd8ac843f14812152fab7dbd45c3388362940`). It is not superseded in place — `v2.1.0-rc.2` is a
new, separate candidate.

`v2.1.0-rc.2` includes everything already validated in `v2.1.0-rc.1` (see
[`v2.1.0-rc.1.md`](v2.1.0-rc.1.md)) plus all work merged since: Sprint 79 (accounting and invoice
readiness), Sprint 80 (VAT-aware sale completion and reversal reporting), the Sprint 81 acceptance
defect fix (outbox dispatcher event-type isolation), and PR #155 (succeeded-refund lifecycle
timestamps, atomic finance posting, and replay-before-validation idempotency), followed by the
completed application and Noctella Web work through Sprint 122.

## Validated capabilities

### Carried forward from v2.1.0-rc.1

- Product and inventory management, with EUR-only pricing and finance throughout
- Product-photo upload, promotion, ordering, primary-photo selection, persistence, and durable
  outbox processing
- Storefront catalog, product detail pages, SEO metadata, sitemap, and robots
- Cart, guest "Make an Offer", mock checkout, and order creation
- Order cancellation with inventory restoration
- SQLite restart persistence
- Stale outbox-lock recovery
- Production-safe mock-payment gate (mock providers disabled by default outside staging)
- Fail-closed marketplace webhook signature verification

### New in v2.1.0-rc.2

- Company profile and invoice issue readiness
- Automatic SalesInvoice Draft creation for eligible paid internal orders, via the durable outbox
- Durable outbox delivery with event-type dispatcher isolation (each dispatcher now claims only
  its own registered event types, closing the cross-claim/false-dead-letter defect found during
  Sprint 81 acceptance)
- VAT-inclusive and VAT-exclusive invoice calculation
- Invoice issue validation
- Post-issue invoice immutability
- Issued-invoice-based sale completion accounting
- Persisted completed-sale financial values: gross revenue, VAT, net revenue, item cost, and
  profit
- Return lifecycle
- Refund lifecycle, internal/manual refund recording, finance posting, and reversal reporting are
  implemented. Real Stripe, PayPal, payment-provider, and marketplace refund execution remain
  unavailable.
- Synchronous/manual Succeeded refund recording, with `submittedAt`/`succeededAt` correctly
  populated (equal, at creation time) for that path
- Atomic `SuccessfulRefund` finance posting (the refund row and its finance entry commit together,
  in the same transaction)
- Idempotent refund creation replay resolved before refundable-balance validation, so a replay of
  an already-fulfilled request is never incorrectly rejected once it has consumed the remaining
  refundable balance
- Full sale reversal, with stock restoration
- Effective post-reversal finance reporting (adjusted financials and the global finance summary
  correctly reflect zero after a full reversal)
- Immutable original sale and invoice snapshots, preserved for audit after a reversal

### Noctella Web capabilities completed through Sprint 122

- Marketplace-neutral public product presentation uses the approved Noctella Web title, long
  description, optional short description, SEO title, meta description, and effective listing
  price with their established canonical fallbacks. Woo-specific storage fields remain private.
- Customer product search includes the approved Noctella Web product name. Customer title and
  price sorting use the effective Noctella Web values with canonical fallback and deterministic
  ID tie-breakers.
- Direct orders use an explicit `noctella_web` pricing context with effective price
  `wooListingPriceEur ?? priceEur`; other order contexts retain their established pricing
  semantics.
- Direct checkout remains EUR-only. Paid amounts are compared using deterministic integer-cent
  normalization, and stale or mismatched checkout/payment data fails closed without silent
  repricing.
- Direct order-item titles use the approved Noctella Web product name with canonical fallback and
  are stored as immutable historical snapshots. Invoice drafting consumes the stored order-item
  title rather than a later product edit.
- Durable order and inventory work completes before post-commit stock synchronization. Repository
  audit tooling enforces that synchronization occurs after the final same-scope UnitOfWork
  transaction.

These implemented customer-facing capabilities do not constitute production payment, deployment,
backup, or database-cutover readiness.

## Manual acceptance already completed

Manual, isolated, local SQLite acceptance has already verified the following exact figures and
behaviors (not yet repeated against a live staging deployment for this candidate — see "Known
limitations" below):

- Purchase landed cost: `42 EUR`
- Sale total: `120 EUR`
- Invoice taxable base: `100 EUR`
- Invoice VAT: `20 EUR`
- Persisted sale financials: gross revenue `120 EUR`, VAT `20 EUR`, net revenue `100 EUR`, item
  cost `42 EUR`, profit `58 EUR`
- Full refund: `120 EUR`
- Full stock and finance sale reversal
- Effective post-reversal financials reduced to zero
- Original sale-financial snapshot and issued invoice preserved, immutable
- Stock movements balance to zero (`sale_out -1`, `return_in +1`)
- No duplicate finance, refund, reversal, invoice, or stock records across any of the above

This is validation evidence from the isolated acceptance already performed, not a claim of
live-environment testing.

## Release status

This release is a **Release Candidate**. Isolated staging acceptance specific to this candidate's
accounting/invoice/refund/reversal behavior has not yet been performed against a live Render
staging environment (see `docs/deployment/render-staging.md`'s "v2.1.0-rc.2 Isolated Accounting
Acceptance" section for the required checklist). It is not yet approved as a production release.

## Known limitations

- Isolated live staging acceptance for `v2.1.0-rc.2`'s accounting/invoice/refund/reversal behavior
  is still pending
- Production deployment is not approved
- Customer payment providers remain mock-only, and production payment-provider operational
  validation has not been performed
- Real Stripe and PayPal integrations are absent
- Real payment-provider refund execution is absent (only internal/manual Succeeded-refund
  recording is implemented — see "New in v2.1.0-rc.2" above)
- eBay, Etsy, and WooCommerce marketplace integrations are not active
- Automated off-disk database backups and automated off-disk photo/object-storage backups do not
  exist; no tested disaster-recovery or off-disk restore drill is available
- SQLite deployment must remain single-instance; horizontal scaling is unsafe under the current
  architecture
- Detailed PostgreSQL schema definitions exist in code, but executable migration parity is
  incomplete. Some migration-created accounting/refund structures remain placeholders relative
  to the current schema definitions, so a deployable PostgreSQL accounting/refund cutover is not
  ready.
- Migration foundations include schema-parity inspection, migration preview/validation, SQLite
  integrity/fingerprint checks, and backup-prerequisite/readiness checks. A complete production
  migration manifest, fully executable PostgreSQL parity, a verified production data-copy
  procedure, a tested rollback manifest, and an off-disk restore drill remain incomplete.
- Production cutover finalization remains deliberately disabled: preview/foundation is available,
  but production cutover is incomplete and unapproved
- CreditNote workflow is absent
- Full double-entry accounting is absent
- Invoice records, drafts, events, and outbox behavior exist, but server-side rendered PDF artifact
  generation and invoice email delivery are absent
- No production marketplace invoicing
- Some non-blocking Admin UX and observability improvements remain deferred
